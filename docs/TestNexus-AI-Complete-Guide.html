1. What TestNexus AI is

TestNexus AI is an intelligent regression testing platform. It reads a pull request, decides which regression tests are worth running for that change, and explains what ran, what was skipped, and why.

The selection rules are deterministic (fixed, repeatable). An optional AI call can add tests. It cannot remove the tests the rules already selected.

One-line story for a resume: “Reads a PR, scores regression risk, picks only the tests that matter, runs them in GitHub Actions on a real order-management stack, and shows the decision in a dashboard.”

2. Big picture: three parts

TestNexus AI (this repo) = the brain (selection + report + dashboard) GitHub Actions (product) = the muscle (starts DB, API, UI, runs Playwright) Dashboard (React + Vite) = the control room (Overview, Suites, PRs, Analysis)

They connect like this:

Pull request opens on the product (OpenOMS) | v GitHub Actions "select" job clones / uses TestNexus runs: npm run analyze -- --project openoms --pr N | v TestNexus writes a report + a Playwright grep pattern | v GitHub Actions "e2e" job starts Postgres, Redis, API, dashboard runs only the selected Playwright tests uploads artifacts (testnexus-report, playwright-results) | v Dashboard / suite runner can show the same runs and decisions

3. What problem it solves

  • Full regression on every PR is slow and expensive.
  • Blindly skipping tests is unsafe.
  • TestNexus maps changed files to features, then to known tests, then scores risk.
  • Small, low-risk changes run a small set. Risky or unmapped source changes keep critical coverage.
  • Every decision is written into a JSON report the dashboard can show.

6. The selection pipeline (step by step)

Implemented in src/core/pipeline.js. Order:

  1. Load pull request summary — from a fixture JSON, or from GitHub (--pr / --project).
  2. Change analysis (analyzePullRequest) — labels each changed file as source, test, configuration, documentation, or other. Understands common extensions including Go and SQL.
  3. Impact analysis — matches file paths to features in the feature map.
  4. Test mapping — finds registry tests for impacted features, and tests whose own file was edited.
  5. Risk scoring — 0–100 score and low / medium / high level.
  6. Selection — keeps mapped tests; if a source file matches no feature, also keeps every critical test (safety net).
  7. Intelligence review — optional AI may add ids; unknown ids are rejected.
  8. Validation — only known registry test ids survive.
  9. Optional local execute — Playwright on the laptop (--execute), only when the project allows local execution.
  10. Failure diagnosis — labels failures as product vs infrastructure when execution happened.
  11. Report — JSON comparing full suite vs deterministic selection vs final selection, with reasons.

7. Risk scoring

ConditionPoints
Critical feature changed40
Other mapped feature changed20
Source file outside the feature map25
Source file removed15
Change size1 point per 5 changed lines, max 20
Configuration changed10
  • Documentation-only change → score 0.
  • Level: low < 25, medium 25–59, high ≥ 60.

8. AI step (optional)

  • Without AI_API_KEY, the system is fully deterministic.
  • With a key, the intelligence engine may suggest additional registry test ids.
  • Suggestions that are not in the registry are rejected.
  • AI cannot drop tests the rules already selected. That is intentional and important for trust.

10. Evaluation and labelled quality

tests/fixtures/evaluations.json holds hand-labelled cases (expected relevant / critical tests for each change). npm run evaluate measures:

  • Precision — of the tests selected, how many were relevant.
  • Recall — of the relevant tests, how many were selected.
  • Critical recall — same idea for critical tests only.
A deliberate miss case (“catalog price change”) is included so the score is not a fake flat 100%. Current story: precision 100%, average recall about 92%, critical recall 100% over 6 cases.

12. Suite runner API (local helper)

  • Process: src/commands/suite-server.js → HTTP server on 127.0.0.1 only.
  • Holds the GitHub token on the server. The browser never sees it.
  • Refuses non-local Origin and non-local Host (blocks cross-site and DNS rebinding).
  • Main routes:
    • GET /api/health
    • GET /api/suites
    • GET /api/suite-runs — suites + recent runs + pull request rows (and writes the local snapshot)
    • POST /api/suites/:id/run — workflow_dispatch (409 if that suite is already running)
  • Vite proxies /api to http://127.0.0.1:4000 in development.

13. Connecting a real product: OpenOMS

OpenOMS is a real industry-style order management system (API in Go, dashboard UI, Postgres, Redis, Playwright suite). TestNexus uses a fork: ApooravSharma01/openoms.

Product profile lives at registry/projects/openoms/:

  • project.json — id, name, repository, execution: "github-actions" (no local --execute).
  • feature-map.json — features (e.g. critical sale-order) and the path prefixes that belong to them.
  • tests.json — SALE-ORDER-001 … 008 with exact Playwright titles, tags, files, critical flags.

In CI, TestNexus is invoked roughly as:

npm run analyze -- --project openoms --pr N --out …
npm run playwright-grep   # turns selected titles into a --grep pattern

If TestNexus itself fails in the select job, the product workflow is designed so the full suite can still run. Skipping tests only happens when TestNexus successfully said so.

14. GitHub Actions workflow on the product

File (on the OpenOMS fork): .github/workflows/order-creation-e2e.yml

Triggers

  • workflow_dispatch — inputs: suite, grep, optional pr_number. Used by humans, CLI, and the dashboard.
  • pull_request — path-filtered to order-related code and the suite itself.

Jobs (conceptually)

  1. select — when PR or pr_number is present: run TestNexus analyze + playwright-grep; upload testnexus-report; output selected count / grep.
  2. order-creation-e2e — start Postgres + Redis, migrate, seed, build/start API, start dashboard, run Playwright with the grep filter, upload playwright-results (and report). Skips the run only when select succeeded and selected count is 0.
Evidence examples used on the Overview page include real Actions runs (for example a small PR that picked 2 of 8 tests, a high-risk PR that ran 8 of 8, and a full regression 8/8 pass). Counts exclude the Playwright login setup project.

15. How to connect a brand-new app

Follow this checklist. You do not need to rewrite TestNexus core for each product.

Step A — Prepare the product

  1. Have automated tests (Playwright is the proven path) with stable titles and useful tags (@smoke, @regression, @api, …).
  2. Prefer a CI workflow that can start the product stack (DB/API/UI) and accept a grep / filter input.
  3. Add a JSON reporter so results can be uploaded as an artifact (OpenOMS writes results/results.json).

Step B — Create a project profile in TestNexus

  1. Create folder registry/projects/<id>/ where id matches /^[a-z0-9-]+$/.
  2. Add project.json: 
    {
  "id": "my-app",
  "name": "My App",
  "repository": { "owner": "ORG_OR_USER", "name": "REPO" },
  "execution": "github-actions"
}
    Use "execution": "local" only if Playwright can run the product on the laptop.
  3. Add feature-map.json — list features with id, name, critical, and path prefixes that belong to each feature.
  4. Add tests.json — one entry per test with:
    • id (stable, e.g. CHECKOUT-001)
    • title (exact Playwright title string used for grep)
    • featureId
    • file
    • critical true/false

Step C — Wire the product workflow

  1. On a PR (or dispatch with pr_number), check out / call TestNexus.
  2. Run analyze with --project my-app --pr N.
  3. Convert the report to a Playwright grep file (npm run playwright-grep or equivalent).
  4. Run Playwright with that filter against the real stack.
  5. Upload:
    • TestNexus report artifact (e.g. testnexus-report containing my-app.json)
    • Playwright results artifact (e.g. playwright-results containing results.json)
  6. Fail-open if TestNexus crashes: still run the full suite rather than silently skipping everything.

Step D — Register suites for the dashboard / CLI

Add entries to registry/suites.json:

{
  "id": "my-app-smoke",
  "label": "My app smoke",
  "description": "…",
  "repository": { "owner": "ORG_OR_USER", "name": "REPO" },
  "workflow": "my-e2e.yml",
  "ref": "main",
  "inputs": { "suite": "my-app-smoke", "grep": "@smoke" },
  "resultsArtifact": "playwright-results",
  "pullRequestReport": { "artifact": "testnexus-report", "file": "my-app.json" }
}

Then:

npm run suite -- --list
npm run suite -- my-app-smoke
# or use the Suites tab after npm run dev:all

Step E — Verify

  1. Unit tests still pass: npm test.
  2. Analyze a known PR: confirm selected ids look right.
  3. Dispatch smoke and regression once; confirm artifacts and dashboard rows.
  4. Open a real PR that touches a mapped path; confirm select → filtered e2e → green or expected fail.

17. Hosting for a resume / public demo

  1. Build only the dashboard: cd dashboard && npm run build.
  2. Host dashboard/dist (GitHub Pages, Netlify, Vercel, …).
  3. Do not host the suite runner with your token on a public URL.
  4. First open shows Overview (pitch + proof). Suites show “not connected” — that is expected and safe.
  5. Keep the TestNexus and OpenOMS repos public if evidence links should open for recruiters.
  6. Resume link tip: https://your-host/#overview (empty path also redirects to Overview).

18. Security rules

  • Token only in local .env / CI secrets — never in frontend code or public artifacts.
  • Suite API binds to 127.0.0.1 and checks Origin/Host.
  • Production builds do not ship the saved suite-runs snapshot.
  • Dashboard cannot invent suites; it can only start ids present in registry/suites.json.
  • Same suite cannot be double-started while already queued/running.

19. Known limits

  • OpenOMS PR path filters mean only certain PRs trigger the workflow automatically.
  • Branch protection is optional; without it, failing checks do not block merges.
  • Jenkins is not connected (dashboard Actions path is the live one).
  • Upstream OpenOMS may have unrelated failing checks (e.g. security tooling / missing secrets) that are outside TestNexus.
  • Zero-selection path is covered in unit tests; treat real PRs with care when mapping is incomplete — unmapped source still pulls critical tests.
